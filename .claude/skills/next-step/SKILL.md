# Следующий шаг MVP

Режим наставника: ты не пишешь код в `src/`, а говоришь пользователю, что сделать.

## 1. Оцени текущее состояние

- Прочитай план в `CLAUDE.md` (экраны, структура `src/`, роуты).
- Сравни план с тем, что уже есть: `src/services`, `src/types`, `src/stores`, `src/composables`, `src/views`, роуты в `src/router/index.ts`, тесты.
- Посмотри `git status` и последние коммиты: возможно, работа уже идёт.
- Отметь остатки scaffold'а, которые пора убрать (`stores/counter.ts`, тест с «You did it!»).

## 2. Выбери ОДИН следующий шаг

Порядок зависимостей по умолчанию:
1. Типы ответов API (`types/football.ts`) по реальным ответам (см. `/api-explore`).
2. API-обёртка (`services/footballApi.ts`) с обработкой ошибок и 429.
3. Store с кэшем и TTL + выбранная команда в localStorage.
4. Роуты и каркас views.
5. Экраны по порядку: выбор команды → дашборд → матчи → таблица → состав.
6. Тесты на store и расчёт формы.
7. Деплой (GitHub Pages + Actions) и решение вопроса с прокси в проде.

Если пользователь передал фокус (`$ARGUMENTS`), учитывай его.

## 3. Формат ответа

- **Где мы сейчас** — 2–3 строки.
- **Следующий шаг** — что и зачем.
- **Инструкция** — нумерованные шаги: какой файл создать, что в нём должно быть (сигнатуры, ключевые идеи, короткие фрагменты-подсказки, а не готовый файл), какие команды выполнить.
- **Как проверить** — критерий готовности: что увидеть в браузере, какой тест должен пройти.
- **Подводные камни** — 1–3 пункта, специфичных для этого шага.

Если для шага нужна документация библиотеки — сверься через context7, прежде чем советовать API.
